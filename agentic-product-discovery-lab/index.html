Agentic Product Discovery Lab · Public Case Study

How I built an AI agent to improve product intake decisions.

I designed and tested an AI product intake analyst that compares incoming requests with existing work, classifies what they mean, exposes evidence gaps, and recommends the next product decision, without removing the product manager from the loop.

01 · The problem

Product intake systems collect requests but they rarely create clarity.

Incoming requests are often vague, duplicative, solution-led, or disconnected from work already underway. The costly part is determining what the customer is actually asking for, whether the problem is already addressed, and what evidence should shape the next decision.

Question I wanted to answer
Can an agent speed up intake analysis while making its reasoning clear enough for a product manager to challenge?
02 · The system

I built a small, controlled product discovery environment.

I built the lab in a personal ClickUp workspace using synthetic product data only. The agent is manually invoked, reviews defined sources, replies in the request thread, and updates only analysis-owned fields.

03 · The decision model

I used two taxonomies because one label couldn’t capture both decisions.

“Duplicate” describes a request’s relationship to existing work. “Defect” describes the nature of the request. Both can be true at once. Separating those judgments produced clearer, more actionable analysis.

A
Axis one

Relationship to Existing Work

Duplicate

The same core problem and intended outcome are already addressed.

Adjacent

Existing work could credibly be extended to solve the same core problem.

Net New

The request introduces a distinct capability or outcome.

No Match Found

The evidence reviewed doesn’t reveal related work.

Needs More Information

The request is too ambiguous for a responsible conclusion.

B
Axis two

Agent Request Type

Feature

New user-facing capability

Enhancement

Improvement to intended behavior

Defect

Existing behavior isn’t working as intended

Discovery / Research

A problem requiring validation before solutioning

Unknown

Insufficient evidence to classify

Critical boundary rule

Adjacent means the same core problem, workflow, outcome, or capability could be addressed by extending existing work. Requests may share a product area, user, data source, or theme and still solve different problems.

04 · The evidence

The tests were designed to expose bad judgment as well as confirm happy paths.

Each synthetic request tested a different kind of mistake: stopping at a duplicate label, confusing an enhancement with a defect, connecting requests that weren’t actually related, or making a confident decision without enough information.

05 · Product decisions

I made the biggest improvements between tests.

Each failure gave me evidence I could use to improve the prototype. I refined the operating model along with the prompt wording.

01

Split the taxonomy

Separated relationship from request type so the output could show both clearly.

02

Tighten adjacency

Replaced broad thematic similarity with a test based on the core problem, workflow, outcome, or capability.

03

Keep “duplicate” useful

Required the agent to surface discoverability, configuration, adoption, usability, or unmet-detail gaps when evidence supports them.

04

Handle uncertainty

Included confidence, evidence reviewed, missing information, and PM review in the output.

06 · Guardrails

I set clear boundaries for the automation.

  • Manual trigger The agent runs only when assigned or mentioned.
  • Defined sources The agent bases its analysis on the designated product context.
  • Field ownership The agent updates analysis fields and preserves requester-entered data.
  • PM review The product manager reviews the recommendations and makes the final decision.
  • Safe lab The experiment uses synthetic data and isn’t connected to production customer data, a codebase, or company systems.
↳
The takeaway

A useful product agent should make its judgment easy to inspect and question.

The lab showed how I’d approach agentic product discovery in a real product environment. I’d define which evidence the agent can use, make its reasoning visible, test the boundary cases, and keep the product manager accountable for the final decision.
